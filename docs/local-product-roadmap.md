# AgentHub 个人本地产品完善路线图

日期：2026-11-09。目标：将 AgentHub 完善为个人开发者可以持续使用的本地软件开发协作产品，同时形成本科软件工程毕业设计的实现与实验材料。

本路线图是后续规划，不替代现有能力契约，不表示下列任务已经完成。涉及实体、接口、安全边界和新依赖的工作，应先形成对应 OpenSpec 变更，再按项目约定确认和实现。论文建议题目为《面向软件开发任务的多智能体协作平台设计与实现》。

## 产品范围与优先级

首发建议支持 Windows x64 桌面应用和本机浏览器，用户自备模型凭据，使用本地项目目录。macOS、Linux 在完成各自安装及真实运行验收后单独列入支持矩阵，不以源码能够运行代替产品支持。

首发核心场景是：在已有 Git 项目中完成小型功能、修复可复现缺陷、补充测试和代码审查。用户提出需求，审核计划，查看执行过程，核对修改与验证结果，再决定接纳交付。非 Git 目录可保留单任务使用；未验证的并行修改能力不默认开放。

首发不包含团队账号、多租户、公网访问、平台代付模型费用、无人值守自动部署、移动端、任意插件市场。文档和网页产物保留现有能力，PPT 等扩展不作为本轮主线。

本地优先指应用数据与工作目录保存在本机；模型调用和联网工具仍可能把选定上下文发送到外部服务。界面必须明确这一边界。

| 优先级 | 定义 | 发布规则 |
| --- | --- | --- |
| P0 | 数据保护、授权、结果可信、可恢复、最低安装可用性 | 阻断对应版本发布；不能以界面提示替代修复 |
| P1 | 日常效率、可维护性、完整交付体验 | 进入稳定版范围；未完成时必须明确限制并缩小发布范围 |
| P2 | 持续自治、更多平台和外部集成 | 稳定版之后推进，不阻塞毕设 |

## 当前基线

基线来自本地分支 `codex/resumable-context-management`，HEAD 为 `ef2c15a`，并包含工作区尚未提交的修改。正式实验须另行冻结已提交版本。远程跟踪信息只代表本地缓存，不作为已核实远端最新状态的证明。

| 能力 | 已有基础 | 需要核实或补齐的边界 |
| --- | --- | --- |
| Agent 接入 | Custom、Claude Code、Codex 适配与统一事件流 | 逐一验证真实模型与安装包内运行；历史记录中 Codex 真实验收存在 TLS/超时未通过项 |
| 编排交付 | DAG、任务契约、上下游产物绑定、执行证据 | 验收证据与最终代码版本绑定，集成后重测；历史任务清单与实际验证记录需对齐 |
| 并发写入 | 同波次 `fs_write` 冲突检测 | bash、SDK 写入未被同一追踪完整覆盖；事后检测不能防止覆盖 |
| 任务恢复 | 检查点、运行日志、暂停续接、消息队列 | 组合故障和副作用不确定性；审批依赖内存，重启失效需重新申请 |
| 状态同步 | 持久化 SSE、游标补发和快照 | 全量快照的数据规模、长时间使用与慢客户端表现 |
| 访问安全 | 本机配对、同源校验、凭据 DTO 脱敏 | shell 在宿主权限下运行，路径与命令规则不是 OS 级执行沙箱 |
| 数据管理 | SQLite、启动迁移、备份部署记录、项目记忆 | 用户可操作的备份恢复、磁盘异常、升级回退和数据清理 |
| 发布验证 | 单元、集成、浏览器和部分真实模型记录 | 干净机器安装、完整升级路径、适配器支持矩阵、持续试用证据 |

依据：[本机个人版规格](../specs/16-local-personal.md)、[编排契约](../openspec/specs/orchestrator/spec.md)、[桌面契约](../openspec/specs/desktop-electron/spec.md)、[写入追踪](../src/server/dispatch-file-writes.ts)、[恢复入口](../src/server/recovery-service.ts)、[审批存储](../src/server/pending-dispatch-plans.ts)、[变更记录](development-change-log.md)。历史测试通过数不能作为新版本的验收结果。

## 阶段总览

工期是单人持续投入下的初步工作量区间，不是交付承诺；模型服务、签名证书和测试设备可能影响进度。以各阶段验收门槛决定是否进入下一阶段。阶段一的安装与安全底线应在任何外部试用之前完成。

| 阶段 | 参考工作量 | 产品里程碑 | 毕设产出 |
| --- | --- | --- | --- |
| 0 基线与选题 | 约 1 周 | 可复现版本、范围和问题清单 | 开题范围、需求、架构与初始指标 |
| 1 数据保护与可控执行 | 约 2–3 周 | 可用于自己的真实项目 | 威胁边界、恢复状态机、故障测试 |
| 2 可验证的协作交付 | 约 2–3 周 | 多任务修改可隔离、可集成、可验收 | 核心设计、实现与对照实验条件 |
| 3 可分发的个人测试版 | 约 2–3 周 | 他人可以自主安装和使用 | 可用性测试、发布与维护设计 |
| 4 稳定版与论文验收 | 约 2 周及连续试用 | 有完整发布证据的个人稳定版 | 实验分析、论文定稿、答辩演示 |
| 5 持续任务扩展 | 稳定版后评估 | GitHub 反馈驱动的持续工作 | 可作为展望，不纳入必须完成项 |

## 阶段 1 数据保护与可控执行

| 编号 | 优先级 | 具体任务 | 验收标准 |
| --- | --- | --- | --- |
| R1-01 | P0 | 统一执行策略，覆盖 Custom、Claude、Codex 的文件/命令入口；明确授权目录和敏感操作；限制未完成隔离的并行写入 | 支持矩阵中的每条执行路径通过越界路径、符号链接或 junction、审批拒绝、取消测试；未覆盖路径禁用或降为明确受限模式；界面不宣称 OS 沙箱 |
| R1-02 | P0 | 建立宿主执行威胁模型；检查子进程凭据和网络工具访问边界 | 浏览器响应、日志、诊断包和检查点无原始 Key；子进程仅接收必要凭据；网页/仓库内容不能自动赋予新权限；联网抓取覆盖本机/私网/重定向限制测试 |
| R1-03 | P0 | 故障注入验证检查点、队列、审批和恢复 | 在模型输出、工具执行前后、审批等待、子任务结束时分别中断；每处至少重复 3 次；已确认完成的副作用不重放，不确定副作用暂停核对，旧审批不可复活 |
| R1-04 | P0 | 任务级资源预算：时间、工具次数、重试次数、并发；可观测 Token 预算与摘要费用归属 | 每种限制都有触发用例；超限后停止新调度并显示原因；取消后测试子进程完成清理；SDK 不可观测调用的预算误差明确展示，不承诺无法实现的金额硬上限 |
| R1-05 | P0 | 完整数据目录备份、恢复与迁移失败处理；保护用户原有修改 | 在副本完成升级及回退演练，消息/产物/配置数量及关键内容一致；磁盘满和中断备份不替换有效备份；真实旧库不使用 `db:push --force` 升级 |
| R1-06 | P0 | 最小安装冒烟和依赖检测，核对模型凭据配置、数据目录及原生模块 | 至少一台无项目开发环境的 Windows x64 机器可启动；缺运行依赖时给出明确修复方式；不读取开发机隐藏配置才能运行 |

阶段出口：通过上述确定性安全与恢复用例后，允许在有备份的个人项目中日常使用。仍不提供无人值守任意命令执行。首发定位为受信任本机用户的辅助工具，不提供恶意代码隔离承诺；若扩大到执行不可信项目代码，必须另行设计并验证 OS 级隔离。

## 阶段 2 可验证的协作交付

依赖阶段 1。代码隔离的具体接口须先形成 OpenSpec 设计；继续沿用统一 AgentRunner，不另建绕过适配器和执行策略的调度通路。

| 编号 | 优先级 | 具体任务 | 验收标准 |
| --- | --- | --- | --- |
| R2-01 | P0 | 为可并行修改的任务设计独立 Git 分支/worktree 或等效工作副本；记录起始 revision | 两个 Agent 修改同一文件互不覆盖；用户未提交修改保持不变；依赖任务获得约定版本的上游结果；非 Git 或不兼容模式自动串行或明确拒绝 |
| R2-02 | P0 | 集成步骤包含差异审核、冲突处理、合并后检查与交付确认 | 无冲突时形成可审查差异；有冲突时保留双方结果并暂停；验收针对集成后的最终版本；清理仅移除本任务创建的副本，不删除用户文件 |
| R2-03 | P0 | 将验收条件、命令证据、产物和最终文件版本绑定 | 缺必需输出、无关测试通过、测试后再次改码三种用例均不得判定已验收；代码变化使旧证据失效；报告能定位版本、命令和结果 |
| R2-04 | P1 | 在已有 run/plan 上明确任务状态与版本关系；增加任务视图 | 用户可区分排队、执行、等待审批/输入、暂停、中断、待验收、完成、失败和取消；刷新与恢复后一致；任务关联计划、子任务、产物、成本和证据 |
| R2-05 | P1 | 明确运行中输入是新任务、当前任务修正还是取消；计划变更使相关审批失效 | 三种意图有可见回执；不会把修正默默当成排队的新任务；修改验收范围后重新确认；保留旧计划供核对 |
| R2-06 | P1 | 规范最终交付报告和人工接管 | 报告包含修改摘要、差异、验证结果、未解决问题、资源消耗与接纳方式；用户可导出并手动继续；模型自述不充当测试证据 |

阶段出口：四类核心场景均至少有一个真实模型端到端案例，失败案例同样保留。达到可演示和可做对照实验的毕业设计核心版本；此时尚不宣称普遍提高效率。

| 编号 | 优先级 | 具体任务 | 验收标准 |

| R4-01 | P0 | 冻结候选版本并完成发布回归 | P0 全部关闭；支持功能对应 P1 通过；无已知数据丢失、越权或错误重复副作用问题；源码、安装包、数据库版本和测试记录对应同一版本 |

稳定版质量门槛与研究结果分开：实验可以表明多 Agent 更慢或某类任务收益有限，只要如实报告；安全与数据完整性失败不能由平均任务成功率抵消。

| 编号 | 任务 | 启动条件与验收方向 |

## 毕设与实验安排

本科论文重点限定为统一适配、依赖调度、任务契约、产物交接、验收和异常恢复。不将接入 SDK 或使用 DAG 本身表述为算法创新。个人贡献应逐项区分已有基础、本人新增设计与实现、引用代码和 AI 辅助内容。

| 论文章节 | 对应工作 | 可留存证据 |
| --- | --- | --- |
| 绪论与需求分析 | 阶段 0 | 场景、用户需求、范围、相关工作资料 |
| 总体设计 | 阶段 0–1 | 五层架构、领域模型、事件流、信任边界 |
| 关键模块设计与实现 | 阶段 1–2 | 调度与恢复状态机、工作副本隔离、任务契约、版本化验收 |
| 系统测试与评价 | 阶段 3–4 | 自动化报告、真实模型记录、故障注入、可用性观察 |
| 总结与展望 | 阶段 4–5 | 适用范围、失败分析、局限及持续任务方向 |

建议对照组：A 为单 Agent；B 为保留基础依赖调度的多 Agent；C 为增加任务契约与版本绑定验收的多 Agent。B 与 C 尽量保持角色、基础提示和调度方式一致，仅改变待研究机制。所有组都保留相同安全边界，不通过关闭安全措施制造对比。

建议冻结 12 个任务，每类场景 3 个，每组每题运行 3 次，共 108 次真实模型试验。先用 2 个独立预实验任务估算成本和时长；预算不足时在正式实验前缩减并公开说明。采用相同模型版本、工具权限、起始代码、任务级总预算、超时和机器资源；记录调度与摘要开销、缓存用量、模型参数与日期，交错运行各组减少时间因素偏差。

指标定义：

- 任务成功率：最终产物通过预先定义且独立检查的全部必需验收条件的试次比例；超时、预算耗尽计入失败，不从分母移除。
- 错误完成率：系统声称完成但外部验收不通过的次数，占声称完成次数的比例；分母为零时报告不适用。
- 人工干预次数：为纠错、补充必要信息、解除阻塞而产生的操作；例行审批单独计数，避免混淆。
- 耗时：从任务提交到最终结果的墙钟时间，同时记录排队、模型执行、工具执行和等待人操作的时间。
- 成本：输入、输出、缓存及摘要 Token；只有存在可核验计价时才给出金额，不跨供应商直接比较 Token 价格。
- 恢复正确性：注入故障后状态、文件与副作用符合预期的次数占比；同时报告重复执行与不确定副作用转人工次数。

结果按任务类别报告成功率、耗时中位数及离散程度、失败原因和预算；小样本不作普遍性结论。功能测试、真实模型实验和用户试用分别出表，mock 通过不计为真实模型任务成功。

开题前一个月建议：第 1 周确定阶段 0 基线与需求；第 2 周整理架构及相关研究；第 3 周完成代表性任务与故障预实验；第 4 周冻结题目、核心范围、方法和进度安排。该安排只要求形成可信开题方案，不要求一个月内完成稳定产品。

## 执行与复盘约定

每个任务独立关联 OpenSpec 变更、代码提交和验收记录。影响实体、事件或安全约束时按项目规则先确认契约；代码修改附简洁、解释原因的标准注释。文档规划不自动授权新增依赖或修改安全边界。

每完成一个任务，核对验收证据和剩余依赖，决定继续、修复或调整范围。遇到关键验收信息缺失，补做验证；遇到实现改变假设，更新路线图而非继续沿用失效计划。每周记录新增问题、关闭问题、风险和下一阶段阻塞项。

代码任务执行适用的 typecheck、lint、针对性测试和必要构建；真实模型与安装包单独验收。数据库测试使用临时库或副本。形成可审查提交后核对远端分支并按既有协作流程同步，保留未提交工作，不将未经验证的混合工作区直接作为发布版本。

证据记录至少包含：任务编号、需求编号、commit、操作系统、安装包/适配器/模型版本、测试输入或任务集版本、预期、实际结果、日志位置、未覆盖范围和复核日期。所有未完成任务默认待开始，禁止根据本路线图文字直接标记完成。
