## 2. SDK 会话与上下文：澄清上一轮结论

### 2.1 用户的理解成立的条件

模型依据本次可见输入生成输出。新的 SDK session/thread 并不意味着“换一个新的 LLM”，也不意味着模型丢失某种私人脑内记忆。session/thread ID 用于 SDK/运行时定位历史、状态和关联资源。

如果新会话得到等价的有效上下文，包括系统/开发者指令、近期消息、摘要、必要工具结果、文件状态、附件及权限，那么单纯换 ID 不必损害任务理解。输出仍可能因采样、工具状态、缓存和实现差异变化，不能保证逐字一致。

恢复旧 ID 也不会让无限历史免费进入模型；SDK/运行时仍需选择、压缩或重建上下文。性能与缓存命中取决于实际实现。

### 2.2 修复前的输入链路（a1a18c8 问题基线）

| Adapter | 当前历史来源 | 重启后的影响 |
|---|---|---|
| Custom | `buildHistoryFor` 从 SQLite 取近期消息、Pin、摘要 | 普通历史仍可重新构造，但受到条数、预算与内容过滤限制 |
| Claude Code | 内存里的 session ID 用于 SDK resume；额外拼已有摘要 | ID 丢失后没有普通历史兜底，界面存在的历史不等于模型已收到 |
| Codex | 内存里的 thread ID 用于 SDK resume；额外拼已有摘要 | 同上；SDK 磁盘历史可能仍在，但 AgentHub 缺少定位关联 |

证据：`src/server/agent-runner.ts` 的 `buildAdapterInput`（约 1990 行）；`src/server/adapters/session-store.ts`；两个 SDK Adapter 的 resume 分支。

示例：用户先说“后端只用 SQLite”，重启前未压缩，重启后只说“继续做登录”。Custom 可能重新取到第一条消息；SDK Adapter 当前可能只发“继续做登录”及项目指令，因而缺失该约束。问题是上下文未恢复，而不是新 ID 本身。

### 2.3 目标契约

- UI 消息历史是展示与重建来源；SDK session 是运行时续接句柄；二者分别持久化。
- 恢复顺序：有效句柄续接 → 明确识别失效/不兼容 → 规范化上下文重建 → 记录上下文来源。
- 不能对任意 SDK 错误自动新建重试；已有工具副作用时必须先核验，防止重复写入/发布。
- 普通历史重建只使用经过筛选的公开输出、必要事实和工具证据，不回放内部思考文本。
- 本期同一 `(conversationId, agentId, adapter)` 建立独立关联；分支隔离留待并行 worktree 阶段，配置指纹决定迁移、继续或重建；模型变化不必一律丢弃上下文。
- 未来团队版在上述键中加入租户/项目范围；当前先实现单用户兼容。

## 3. Key 被盗的访问边界分析

### 3.1 修复前已确认的源码事实（a1a18c8 问题基线）

| 文件 | 行为 |
|---|---|
| `electron/server-bootstrap.ts:15` | 伴随模式启用且有设备令牌时，整个 Next standalone 服务监听 `0.0.0.0`；否则绑定 `127.0.0.1` |
| `src/server/mobile-auth.ts` | 在显式调用该函数的移动 API 上校验 Bearer token |
| `src/app/api/settings/route.ts:6` | GET 未鉴权，返回 `getAppSettings()` 原始对象；PATCH 返回更新后的对象 |
| `src/server/settings-service.ts` | 对象包括数据库里配置的服务商 Key、地址和伴随令牌 |
| `src/app/api/agents/route.ts` | GET 未鉴权，返回 Agent 列表 |
| `src/server/agent-service.ts:173` | 查询 Agent 全行；行中可能包含 per-agent `apiKey` |
| `src/app/api/stream/route.ts` | 未鉴权地订阅全局事件流 |

读取设置接口不等于自动读取所有环境变量：仅设置表存在的值会经这一路返回；环境变量中的 Key 需另查运行环境、日志及工具访问路径。不要扩大未经证实的泄露范围。

### 3.2 一条成立的泄露链路

```text
网络中的访问者
  → 能连接 AgentHub 主机端口
  → 请求普通 /api/settings 或 /api/agents
  → 路由没有要求身份验证
  → 服务端将数据库对象序列化为 JSON
  → 响应中包含 Key
  → Key 被拿到服务商接口使用，产生你的账单
```

不需要破解 SQLite，也不需要先通过手机端配对。前端把输入框显示成星号不会改变 HTTP 响应内容。

`0.0.0.0` 表示监听所有 IPv4 网卡，并不自动意味着公网可达。公网暴露还取决于端口映射、反向代理、隧道、云防火墙、路由器和主机防火墙；局域网或 tailnet 中有访问能力的设备同样需要考虑。当前源码不能证明历史攻击者的入口、IP 或时间。

CORS 是浏览器跨来源读取规则，不是服务端身份验证。直接 HTTP 客户端不受浏览器 CORS 限制。HTTPS 保护传输过程，也不会阻止服务器把 Key 返回给未授权请求。仅加密数据库同样不能修复“接口主动解密并返回”的问题。

还需检查设置修改、Agent provider/base URL 修改等入口：未经授权更改模型 endpoint 可能影响后续凭证和上下文发送对象。此项为需要纳入复现的风险面，尚未证明在本次事件中发生。

### 3.3 立即止损（操作清单，不代表已完成）

1. 在实际使用的服务商后台撤销被盗 Key，检查异常用量并联系服务商处理；记录 Key 标识与时间，不记录完整 Key。
2. 在修复前关闭公网映射/隧道或停止对外服务。若通过 UI 关闭伴随模式，要重启并验证监听地址；当前绑定发生在启动阶段，改设置不会自动改变已打开的监听 socket。
3. 新 Key 在边界修好后再保存到 AgentHub。按服务商能力设置最小权限、限额和异常用量告警。
4. 如果伴随令牌可能通过设置响应泄露，同时撤销/轮换令牌并重新配对设备。
5. 保存反向代理、隧道、主机和服务商日志，核对时间线；检查已有 endpoint 配置和可疑任务。保留证据，避免为排查打印完整凭证。

没有日志只能确定代码存在缺口，不能确认历史根因。后续复现使用隔离数据库和占位 Key，禁止请求真实设置接口后将响应打印到日志。

### 3.4 修复设计

推荐分两期，先解决当前暴露，再演进进程架构。

**一期：保持单个 Next 服务，默认拒绝未认证的业务请求。**

- 建立全路由访问清单：设置、Agent、会话、消息、搜索、SSE、附件、产物、导出、部署、目录访问、审批、内部 MCP 路由。
- 明确最小公开入口：配对启动/健康检查等；配对需短时一次性码、本机确认及限流。公开部署内容必须走明确允许的公共产物路径，不能顺带暴露应用管理入口。
- Web/Electron 使用安全建立的会话；同源 SSE 可使用 HttpOnly 会话 Cookie。跨设备 fetch-SSE 可使用 Authorization；不要把长期 Bearer token 放 URL。会话采用 Cookie 时补 CSRF、Origin/Host 校验和相应 Cookie 属性。
- 配对设备身份与管理员身份分开；移动设备只能执行授权的查看/发消息/审批动作，不能默认改全局 Key 或 provider 地址。
- 凭证只写入，读取 DTO 返回 `configured`、可选指纹/末尾标识。覆盖 GET、POST、PATCH、列表、错误响应、移动快照、日志和导出，避免只修一个 GET。
- 服务端凭证访问与展示 DTO 分离，不能让前端类型直接复用含敏感列的数据库行。
- 令牌撤销后终止或重新验证已有 SSE/长连接。禁止凭证、Authorization、模型上下文原文进入默认审计日志。
- 对配置修改采用字段级授权；provider 地址变化需要管理员权限及可追踪记录。

**二期：桌面管理面与远程设备入口分离。**

- 管理服务继续只监听 loopback；独立远程入口只转发允许的设备操作。
- 远程入口仍须认证和授权，loopback 也不等于自动可信；受控启动握手、Origin/Host 和 Electron 导航限制作为补充。
- 可使用 TLS 或经过正确 ACL 配置的安全隧道，网络控制作为额外防线。
- 单用户凭证存储方案与项目现有 SQLite 约定兼容；是否引入 OS 凭证库另立 ADR，不作为 HTTP 泄露修复的前置条件。
